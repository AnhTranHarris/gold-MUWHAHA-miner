# R9 Durable Research Runner v2\n\nHeavy research is a six-gate state machine, not a single long Chat/tool call.\n\n1. PREFLIGHT — verify script allowlist, free disk, required Python modules, input files, optional input SHA-256, and stale locks.\n2. COMPUTE — run one bounded unit with PID, heartbeat, and explicit per-job timeout.\n3. VALIDATE — require declared outputs to exist and satisfy minimum-size contracts.\n4. LOCAL_COMMIT — atomically write final manifest, hashes, and logs before the worker exits.\n5. REMOTE_SYNC — daemon commits per-attempt manifests/logs/results to the dedicated GitHub branch and retries push failures.\n6. SCIENTIFIC_SYNC — ChatGPT Work/Chat reconciles the completed job into Drive/Library and the research ledger before dependent work is promoted.\n\n## Additional fault containment\n\n- A JSON lock records host, PID, and attempt. Dead stale locks are quarantined automatically.\n- FAILED_RECOVERABLE no longer blocks a job forever. The daemon retries up to max_attempts after retry_backoff_seconds.\n- Every attempt keeps immutable manifest_attempt_NNN.json and worker_attempt_NNN.log evidence.\n- The daemon has its own heartbeat independent of the child research process.\n- R9-Durable-Watchdog runs every two minutes and restarts the daemon if its heartbeat is stale or the scheduled task is not running.\n- A job timeout kills only that bounded worker; later jobs do not inherit its in-memory state.\n- Completed jobs are never rerun automatically.\n- Heavy raw-tick jobs remain sequential. Lightweight post-processing may be parallelized only after inputs are already durable.\n- A dependent stage cannot start from STARTED or RUNNING_VERIFIED; it requires COMPLETED_LOCAL or VERIFIED_DURABLE.\n\n## Job-spec safety fields\n\nRecommended fields: timeout_seconds, heartbeat_seconds, stale_lock_seconds, max_attempts, retry_backoff_seconds, min_free_gb, required_modules, required_inputs, required_outputs, artifact_globs, publish_files, and publish_max_mb.\n\nrequired_inputs and required_outputs may reference R9_* environment paths. This allows the same job to fail closed before expensive compute when data, modules, disk, or expected parent checkpoints are missing.\n\n## Failure ownership\n\nChatGPT is the research director, not the long-process owner. Windows Task Scheduler owns daemon lifetime. The job wrapper owns child lifetime and completion bookkeeping. GitHub owns code and attempt history. Library/Drive owns scientific durability. Work is preferred for long ChatGPT-side orchestration because OpenAI documents that Work can continue remotely after the user leaves, but Work remains an orchestration layer rather than the sole compute owner.\n\nNo layer is assumed infallible; the design is recoverable across a single-layer failure.
